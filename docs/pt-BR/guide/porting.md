# Portar uma correção para outra versão

[English](../../guide/porting.md) | Português (Brasil)

Muitas placas da família X99 usam imagens AMI Aptio relacionadas. Um defeito corrigido em uma versão pode estar em outro deslocamento na sua. O bme nunca aplica patches a um módulo cujo hash difere de uma origem registrada; primeiro é necessária uma variante para sua versão.

1. Leia o chip (`bme guide flashing`) e execute `bme scan dump.bin`. Em uma versão desconhecida, `likely-present` indica que cada assinatura de hunk de um registro correspondeu exatamente uma vez. Os detectores de achados do catálogo também rodam em versões desconhecidas: um acerto `likely-present` indica os módulos que contêm o defeito e onde derivar a variante.
2. Extraia o módulo: `bme extract dump.bin --guid <ffs_guid> -o Module.pe`. Para ver quais módulos da sua versão diferem da versão de referência, execute `bme compare reference.bin dump.bin`: um par `identical-after-normalization` tem o mesmo código em outra base de imagem, então os deslocamentos da referência ainda valem; os bytes normalizados servem apenas ao relatório e nunca são gravados em uma imagem.
3. Analise-o e ao módulo de referência: `bme tools analyze --project work/p --output work/x Module.pe` (`bme guide ghidra`).
4. Gere deslocamentos preliminares: `bme derive --patch B02-B03 --from-firmware mnx99mr9apro-230322 --component UncoreInitPeim --module Module.pe > draft.json`. O rascunho é marcado como `UNREVIEWED`. Ele obtém deslocamentos, bytes originais e contexto do seu módulo e mantém os bytes de substituição da referência. `review_offsets` lista hunks cujos bytes originais diferem da referência (endereços ou deslocamentos mascarados); seus bytes de substituição quase certamente precisam ser recalculados. Hunks não listados ainda podem conter endereços da referência.
5. Para cada hunk, localize-o nas duas exportações `.asm`, confirme que a função ao redor faz o mesmo, recalcule endereços e deslocamentos e desmonte os bytes modificados.
6. Adicione um perfil de placa e uma versão de firmware para sua placa, adicione o componente revisado em `variants.<your-firmware-id>`, remova o campo `draft` e execute `bme catalog index` e `bme catalog validate`.
7. `bme scan dump.bin --catalog ./my-catalog --allow-unsigned-local` deve informar `present`, e uma imagem gerada deve informar `fixed`.

Registre uma observação de hardware somente para uma imagem que você tenha gravado, com seu hash.

Para ver quais métodos ACPI diferem, execute `bme compare --acpi A B`, onde A e B são imagens de ROM, tabelas `.aml` brutas ou um diretório de `bme diag acpi capture` (`bme guide diagnostics`), o que compara o que a máquina em execução publicou com o que a imagem guarda. As tabelas são pareadas por assinatura mais o ID de tabela do OEM. Para cada par, o bme percorre o namespace AML sem executá-lo e lista os métodos e objetos nomeados adicionados, removidos ou alterados, pelo caminho completo gravado na tabela (nomes com preenchimento, como `\_SB_.PCI0`). `--objects` lista também todos os objetos de cada tabela com um hash. `--disassemble DIR` executa ainda `iasl -d` e grava um diff unificado por método alterado em `DIR`; exige `iasl` no `PATH` (pacote `acpica-tools`, listado como linha opcional por `bme tools status`) e se recusa a sobrescrever arquivos existentes. Sem `--disassemble` o bme nunca chama o `iasl`. A varredura lê só declarações, então um método definido condicionalmente dentro do corpo de outro método não aparece.
